# 后台生成与并行运行 —— 设计文档

**日期：** 2026-08-27
**来源：** 真人使用中发现的两个问题——生成过程中切换标签页或关闭面板会中断生成；以及想同时对多个岗位并行生成，不必等一个跑完再开下一个。

## 目标

把一次"生成"从面板里搬到后台，让它**不再依赖面板存活**。这同时解决三件事：

1. 关掉面板、切换标签页、在标签页里导航——生成都继续跑
2. 多个岗位可以**同时**生成（上限 5 个），用户不用排队
3. 每个标签页的面板拿到**独立实例**，A 页和 B 页的内容互不干扰

**不在本轮范围内：** 分数不提升的问题（另一个 spec）；额度用满后的引导与分级配额（第三个 spec，依赖邮件服务，最大）。

---

## 一件明确做不到的事，以及为什么不做

用户最初的表述是"有的页面有插件，有的页面没有"。**按网址决定某个标签页启不启用面板，本轮不做**，理由有两条，不是偷懒：

1. **需要 `tabs` 权限。** 要按 URL 决策就得读到 `tab.url`，而没有 `tabs` 权限时 `chrome.tabs` 返回的对象里 `url` 是空的。用户在上一轮已经**明确拒绝**加这个权限（代价是安装提示多一条 "Read your browsing history"）。
2. **会把自己的路堵死。** 面板一旦在非招聘网站上被禁用，用户就再也没有入口在一个新网站上点「Read this site」授权了——而那正是这个扩展覆盖白标 Workday 之类站点的唯一办法。

**而且这个需求的动机本身会被本轮消解。** 用户要它是因为"关掉 B 页的面板，A 页正在跑的生成就断了"。生成搬到后台之后，这个因果不再成立。

**改为做的是：每个标签页拿到自己的面板实例。** Chrome 官方 API 文档明确支持：

> if the same path is set for this tabId and the default tabId, then the panel for this tabId will be a different instance than the panel for the default tabId.

即 `chrome.sidePanel.setOptions({ tabId, path })`。**不需要任何新权限**——`tabId` 来自标签页事件，不需要读 URL。面板仍然在所有页面可用，但 A 和 B 的状态彼此独立。

**已知代价，用户已确认接受：** 侧边栏是窗口级 UI，同一时刻只显示一个。切走再切回来时，面板**不会自动重新弹出**（Chrome 要求打开侧边栏必须有用户手势），需要再点一次图标。

## 架构

### 运行归属岗位，不归属标签页

一次运行以 **JD 网址**为 key，复用现有的 `cacheKey(rawUrl)`（`extension/src/lib/cache.ts:74`，会剥掉 hash 和 `utm_*`/`ref`/`source`/`trk` 参数）。

**后果，都是刻意的：**
- 关掉标签页，生成继续跑完，结果进缓存——额度不会白花
- 在同一个标签页里导航走，同上
- 下次再打开那个岗位页，结果就在那里（现有的按 URL 缓存已经是这个行为）

### service worker 持有运行

`runTailor`（`extension/src/lib/run.ts:60`）**逻辑本身不改**，只是改由 service worker 调用，而不是面板。它已经是 `(jd, resume, onUpdate, opts)` 的形状，`onUpdate` 正好可以换成"写进 storage"。

### 状态通过 `chrome.storage.local` 广播，不用消息通道

这是本设计里最重要的一个选择，理由：

- **面板随时可能被销毁**，消息通道会随之断开，重开的面板需要一套握手来重新拿到状态
- **storage 是持久的**：新开的面板直接读当前状态即可，零握手
- **`onChanged` 会广播到所有扩展上下文**，天然支持多个面板同时看
- 这套机制**上一轮刚验证过**（登录信号就是这么做的），不是新赌注

写入频率不是问题：一次运行只有 `reading → comparing → writing → done` 四个阶段，加上失败分支，最多 5 次写。

**发起运行**用 `chrome.runtime.sendMessage`（一次性命令，天然适合请求-响应）。

### 数据形状

新增 `extension/src/lib/liveRuns.ts`，与 `cache.ts` 平级、职责分离（`cache.ts` 存**已完成**的结果，`liveRuns.ts` 存**进行中**的运行）：

```ts
export interface LiveRun {
  /** RunState 的全部字段，直接复用 —— 面板已经会渲染它 */
  state: RunState;
  /** 这次运行针对的岗位标题/公司，供将来做汇总视图时用，现在只用于调试 */
  jdTitle: string;
  /** 毫秒时间戳，最后一次状态更新的时刻。见下面的"僵尸运行"一节 */
  updatedAt: number;
}
```

存储键 `cp_live_runs`，值是 `Record<cacheKeyedUrl, LiveRun>`，与 `cp_results` 的组织方式一致。

### 僵尸运行：MV3 的真实风险，必须处理

MV3 的 service worker 空闲约 30 秒会被回收。进行中的 `fetch` 会续命，所以正常情况下一次约一分钟的生成能跑完——**但不能假设它一定活到最后**（浏览器重启、崩溃、Chrome 主动回收都可能）。

**如果不处理，后果是面板永远转圈**：storage 里那条记录卡在 `phase: "comparing"`，没有任何东西会把它推进到终态。这正是本项目反复踩的那类"不报错、但永远不对"的坑。

**处理办法：** 每条 `LiveRun` 带 `updatedAt`。**读取时**（不是写入时）判断：若 `phase` 仍是进行中的阶段，且 `Date.now() - updatedAt` 超过 `STALE_RUN_MS`，则视为失败，向用户显示"生成中断了，请重试"。

`STALE_RUN_MS` 定为 **5 分钟**。依据：实测一次生成约一分钟，5 分钟给足了慢网络和模型抖动的余量，同时又不至于让用户对着一个死掉的转圈等太久。

判断放在读取侧而不是写入侧，是因为**没有任何东西保证"写入侧"还活着**——如果 SW 已经死了，它不可能来把自己标记成失败。只有读取方（面板）一定是活的。

### 失败要落盘

用户选择了"跨运行的进度/失败先不做任何提示"（YAGNI）。**但失败状态本身必须持久化**，否则后台跑失败之后什么都不留，用户切回那个岗位页看到的是一片空白——**比现在还糟**，因为现在至少面板里能看到错误。

所以 `LiveRun` 的终态分两种：
- **成功**：结果写入 `cp_results`（现有缓存），并从 `cp_live_runs` 中删除
- **失败**：`state.error` 保留在 `cp_live_runs` 里，直到用户重试或清除

### 并发上限 5

**硬约束来自服务端限流**：每 IP 30 次请求 / 60 秒（`src/lib/rate-limit.ts:9-10`）。一次生成是 3 个调用（parse-jd、analyze、tailor），所以 10 个并行正好把限流打满，之后所有请求开始被拒。

5 个并行 = 15 次调用，留足余量。而且这个数字与登录用户**每天 5 次**的额度天然吻合——超过 5 个并行对普通用户没有意义，因为额度本来就用完了。

**达到上限时的行为：** 新的生成请求被拒绝，面板显示"同时最多 5 个岗位在生成，请等一个完成"。不排队——排队会让用户以为点了没反应，而且排到时上下文（简历、补充信息）可能已经变了。

## 组件划分

| 文件 | 职责 |
|------|------|
| `extension/src/lib/liveRuns.ts`（新） | `cp_live_runs` 的读写 + 僵尸判定。纯数据层，不含业务逻辑 |
| `extension/src/background/runs.ts`（新） | 运行注册表：启动、并发上限、把 `onUpdate` 写进 storage、终态时转交给 `cache.ts` |
| `extension/src/background/index.ts`（改） | 注册 `runtime.onMessage` 处理"启动运行"；注册标签页事件调用 `sidePanel.setOptions` |
| `extension/src/sidepanel/App.tsx`（改） | 不再自己调 `runTailor`；改为发消息启动 + 订阅 storage |
| `extension/src/lib/run.ts` | **不改**。逻辑原样复用，只是换了调用方 |

`run.ts` 不改是刻意的：它是这个分支上被 review 过最多次的文件之一，改它等于把已经验证过的东西重新置于风险中，而本轮没有任何需求要求改它的内部逻辑。

## 错误处理

- **`runTailor` 内部的失败**（配额、限流、网络、session 过期）：已有的 `ApiErrorKind` 机制不变，写进 `LiveRun.state.error`，面板照现有方式渲染
- **service worker 被回收**：由僵尸判定兜底，见上
- **storage 写入失败**：与项目现有做法一致——记录结构化 `console.warn`，不抛。一次状态更新丢失会由下一次更新覆盖；若是终态那次丢失，僵尸判定会兜住
- **面板发消息时 SW 未唤醒**：`chrome.runtime.sendMessage` 会唤醒 SW，这是 MV3 的标准行为，不需要特殊处理

## 测试

**能测的**（`extension/src/lib/__tests__/liveRuns.test.ts` 新增，以及现有的 `App.test.tsx`）：

- 僵尸判定：`updatedAt` 超过 5 分钟且仍在进行中 → 读出来是失败态；未超过 → 原样返回；已是终态 → 不受时间影响
- 并发上限：第 6 个启动请求被拒，且前 5 个不受影响
- 面板挂载时从 storage 读到进行中的运行并显示进度
- `storage.onChanged` 推进阶段时面板跟着更新
- 成功终态：结果进 `cp_results`，从 `cp_live_runs` 消失
- 失败终态：错误留在 `cp_live_runs`，切回该岗位页能看到

**测不了的**（必须真机验证，报告里要明说，不能拿绿色构建冒充）：

- service worker 的真实回收行为——**这是本设计最大的未验证假设**
- `sidePanel.setOptions({tabId})` 的真实多实例行为，以及切走再切回时面板到底会不会自动重开
- 关闭标签页后生成是否真的继续
- 5 个并行时是否真的不触发服务端限流

## 风险

**最大的风险是 service worker 生命周期。** 整个设计建立在"进行中的 fetch 能让 SW 活到生成结束"这个假设上。这个假设有 Chrome 文档支撑，但**本仓库无法验证**。僵尸判定是兜底——它保证最坏情况下用户看到的是"中断了，请重试"，而不是永远转圈。即便如此，如果 SW 频繁被回收，这个功能的实际体验会比设计预期差很多，需要真机测过才知道。

**次要风险是 `setOptions({tabId})` 的多实例语义**。Chrome 文档的措辞明确，但"切走之后原实例是否存活"文档没说。如果实际上切走就销毁，那么"每标签页独立实例"的价值只剩下"状态不串"，而所有的运行连续性都要靠后台——好在后台正是本设计的主体，所以即使这条假设落空，核心目标依然成立。
